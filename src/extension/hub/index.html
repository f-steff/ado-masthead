Why use an external broker?
  • Authenticates every event before it can queue a review.
  • Avoids relying on a public Incoming Webhook endpoint and an unguessable name.
  • Validates, filters and deduplicates events in one controlled place.
  • Keeps retries, delivery logs and health checks outside Azure Pipelines.
  • Restricts which projects, repositories and events may queue reviews.
  • Lets you rotate broker credentials without changing Azure DevOps service hooks.

Trade-off: you host and monitor one more service. Native mode needs no external hosting.

The broker secret is used only for the create or remove service hook request in this browser. It is not stored in extension data, logs or the page URL.

Event delivery never carries provider credentials. The central review pipeline always needs its provider key, in native and external broker modes, in the Azure DevOps secret variable group masthead-secrets. See the pipeline secret setup.

Install or delete review pipeline

Write the bundled Masthead YAML into a trusted repository and create the pipeline definition, or use an existing YAML file. Native webhook mode needs the native template and an Incoming Webhook service connection named MastheadPR.

Writing YAML commits only the selected Masthead template to the selected repository. Deleting removes only the pipeline definition, not repositories, YAML files or pull request threads.

About Masthead

Version loading...

Use General to set the organization master switch and the defaults used when new projects and repositories are discovered. The project table lets an organization administrator disable reviews for one project without changing its repository settings.

Use Setup to choose event delivery, identify the central review pipeline, and validate that the pipeline is readable by the current identity.

Use Review profile to choose the default provider, model, reasoning options, lenses and review guide. Model suggestions come from the separate hourly catalogue pipeline and remain editable for custom names. Projects and repositories can inherit or override provider and lens choices. Use Examples to preview the input and expected output for every lens, and Permissions to see every requested scope and why it is needed.

Repository-level switches live under each project's Project settings > Masthead page. A pull request is reviewed only when the organization, project and destination repository are all enabled. This also applies when the PR originates from a fork or another project: the destination repository supplies the gate.

Provider keys are never entered in this browser page. Keep the provider key in an Azure DevOps secret variable group linked only to the central review pipeline.

By default, comments use the pipeline's build-service identity. To show a dedicated review identity, create a service account and supply its short-lived PAT as the secret MASTHEAD_ADO_TOKEN; do not use your personal daily PAT.

The Masthead pull request tab shows the effective profile, gating state and thread counts for the current PR. Setup can commit the trusted review pipeline YAML and create the pipeline definition. Project settings can enable or remove only the Masthead completion gate.
